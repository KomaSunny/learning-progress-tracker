### 2. プロジェクト概要

- **システム名**：学習進捗管理アプリ
- **システムの目的・背景**：
  - オンラインスクールの生徒が、日報や進捗報告を記録し、自分の過去の学習内容を振り返れるようにする。
  - 現状、日報はDiscord、進捗報告はGoogleフォームで行っているため、過去の投稿を生徒自身が一覧で振り返りにくい課題がある。
  - 本アプリでは、生徒は自分の進捗報告を作成・一覧表示・編集・削除できるようにする。
  - 講師は、生徒全員分の投稿を一覧表示できるようにする。
  - `student` / `teacher`　のroleによって表示内容・利用できる機能を分離し、認証・認可の要件を満たす。
  - 投稿には `type` を持たせ、将来的に日報と進捗報告を区別できるようにする。MVPでは進捗報告を基本とし、投稿種別の切り替えは実装できる範囲で対応する。
- **関係者**：
  - 講師：生徒の学習状況を確認する
  - 利用者：オンラインスクールの生徒
  - 開発チーム：TeamC

### 3. 用語定義

| 用語     | 定義                                                                    |
| -------- | ----------------------------------------------------------------------- |
| MVP      | 最初に実装する最小限の機能範囲                                          |
| 投稿     | 生徒が学習内容や進捗を記録するデータ                                    |
| 日報     | その日の学習内容や取り組みを記録する投稿                                |
| 進捗報告 | 学習の進み具合、困っていること、次にやることなどを記録する投稿          |
| 投稿種別 | 投稿を分類するための種別。`daily_report` / `progress_report` を想定する |
| student  | 投稿を作成し、自分の投稿を確認・編集・削除できる生徒ユーザー            |
| teacher  | 生徒全員分の投稿を一覧表示できる講師ユーザー                            |
| role     | `student` / `teacher` など、ユーザーごとの権限種別                      |
| JWT      | ログイン済みユーザーを識別するための認証トークン                        |
| CRUD     | 作成、取得、更新、削除の基本操作                                        |

### 4. 業務フロー（As-Is / To-Be）

- **現在の業務（As-Is）**：
  - 日報はDiscordに投稿している。
  - 進捗報告はGoogleフォームで行っている。
  - 過去の自身の投稿を生徒は一覧で振り返れない。

- **新システムでの業務フロー（To-Be）**：
  - 生徒または講師がログインする。
  - 生徒が日報・進捗報告を作成する。
  - 生徒は自分の投稿一覧を確認する。
  - 生徒は自分の投稿を編集・削除する。
  - 講師は生徒全員分の投稿を確認する。

### 5. 機能要件

| ID     | 機能名         | 概要                                 | 詳細仕様                                                                                            |
| ------ | -------------- | ------------------------------------ | --------------------------------------------------------------------------------------------------- |
| FR-001 | ログイン機能   | ユーザーがログインできる             | `student` / `teacher` アカウントでログイン、メールアドレス＋パスワードで認証、JWT 利用              |
| FR-002 | ログアウト機能 | 　ユーザーがログアウトできる　       | 　フロントエンド側で保持しているJWTを削除、ログイン画面へ戻る　                                     |
| FR-003 | 投稿作成       | 生徒が投稿を作成できる               | `student` のみ作成可、入力内容をバックエンドAPIへ送信し、DBに保存、 投稿には `type` を持たせる      |
| FR-004 | 投稿一覧表示   | roleに応じて投稿一覧を表示する       | `student` は自分の投稿のみ表示、`teacher` は生徒全員分の投稿を表示                                  |
| FR-005 | 投稿編集       | 生徒が自分の投稿を編集できる         | `student` は自分の投稿のみ編集可、他人の投稿は編集できない。`teacher` や管理者による編集はMVP対象外 |
| FR-006 | 投稿削除       | 生徒が自分の投稿を削除できる         | `student` は自分の投稿のみ削除可、他人の投稿は削除できない。`teacher` や管理者による削除はMVP対象外 |
| FR-007 | 権限別表示制御 | roleによって利用できる機能を分離する | `/dashboard` で `student` と `teacher` の表示内容を切り替える                                       |

### 8. データ要件

- ユーザー情報を管理する。
- 投稿データを管理する。
- ユーザー権限として `student` と `teacher` を想定する。
- 投稿データは、ログイン中のユーザーと紐づけて保存する。
- 投稿には `type` を持たせ、`daily_report` または `progress_report` を管理できるようにする。
- MVPでは `progress_report` を基本とし、投稿種別の切り替えUIは実装できる範囲で対応する。
- MVPでは新規登録画面を実装しないため、`student` / `teacher` ユーザーは初期データとして事前に作成する。

> 詳細は [`DB 設計`](./DB設計.md) を参照。

### 9. 外部連携・API 要件

MVPでは外部サービス連携は行わない。
アプリ内部のAPIとして、以下を利用する。

| API             | 概要                               | 方法     | 形式 |
| --------------- | ---------------------------------- | -------- | ---- |
| `/auth/login`   | ログイン処理                       | REST API | JSON |
| `/me`           | ログイン中ユーザー取得             | REST API | JSON |
| `/reports`      | roleに応じた投稿一覧取得・投稿作成 | REST API | JSON |
| `/reports/{id}` | 投稿詳細取得・編集・削除           | REST API | JSON |

> 詳細は [`API 設計`](./API設計.md) を参照。

### 10. 制約事項・前提条件

- フロントエンドは Next.js / TypeScript を利用する。
- バックエンドは Python / FastAPI を利用する。
- DBは PostgreSQL を利用する。
- ORMは SQLAlchemy または SQLModel を検討する。
- 認証方式は JWT を利用する。
- MVPでは新規登録画面は実装しない。`student` / `teacher` ユーザーは初期データとして事前に作成する。
- 1週間のMVP開発では、投稿の作成・一覧表示・編集・削除と、role別の表示制御を優先する。
- `/dashboard` は `student` / `teacher` 共通画面とし、roleによって表示内容を切り替える。
- MVPでは `teacher` は生徒全員分の投稿を一覧表示できるが、投稿の作成・編集・削除などの管理者機能は対象外とする。
- 投稿には `type` を持たせるが、投稿種別の選択UIは実装できる範囲で対応する。
- 講師向けの一覧表示画面での絞り込み、ステータス管理、専用管理画面は Good to have とする。

### 11. リスクと対応方針

- 認証・認可の実装が複雑になる可能性がある
  - MVPでは、`student` は自分の投稿のみ作成・一覧表示・編集・削除でき、`teacher` は生徒全員分の投稿を一覧表示できる範囲に絞る。
- 投稿種別の切り替えUIまで実装する時間が足りない可能性がある
  - DB/APIには `type` を持たせるが、画面での選択UIが間に合わない場合は `progress_report` をデフォルト値として扱う。
- 画面数が増えて実装範囲が広がる可能性がある
  - `/login`、`/dashboard`、`/reports/new`、`/reports/{id}/edit` を優先し、`/dashboard` のrole別表示で対応する。
- バックエンドとフロントエンドの接続で時間がかかる可能性がある
  - API設計を先に整理し、必要なエンドポイントとリクエスト/レスポンスを明確にする。
- 講師向けの詳細な管理機能まで実装する時間が足りない可能性がある
  - MVPでは `teacher` が生徒全員分の投稿を一覧表示できるところまで実装し、絞り込み、ステータス管理、専用管理画面はGood to haveとして扱う。
