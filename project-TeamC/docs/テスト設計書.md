# テスト設計書

## 1. テスト方針

本プロジェクトでは、1週間のMVP開発において、認証・認可、投稿CRUD、フロントエンド・バックエンド・DB間の接続が正しく動作することを重点的に確認する。

自動テストの網羅性よりも、Docker Compose環境で実際のAPIとPostgreSQLを利用し、主要なユーザー操作が成立することを優先する。

主な品質ゴールは以下とする。

- `student`が自分の投稿を作成・取得・編集・削除できる
- `teacher`が生徒全員分の投稿を一覧・詳細表示できる
- roleに応じて許可されていない操作が拒否される
- JWTによる認証状態が正しく管理される
- frontend、backend、dbが連携して動作する
- エラー発生時に適切な表示・レスポンスとなる

自動テストのカバレッジ目標は、今回のMVPでは設定しない。

## 2. テスト種別と範囲

| 種別             | 対象                                  | 確認方法                                     |
| ---------------- | ------------------------------------- | -------------------------------------------- |
| APIテスト        | 認証API、投稿CRUD API                 | Swagger UIおよびフロントエンドからの手動確認 |
| 結合テスト       | frontend、backend、PostgreSQL間の連携 | Docker Compose環境での手動確認               |
| 認証・認可テスト | JWT、student／teacherのrole制御       | role別テストユーザーによる確認               |
| 画面テスト       | 画面表示、遷移、入力、エラー表示      | ブラウザによる手動確認                       |
| データ永続化確認 | 投稿データの保存と再取得              | 投稿後の再読み込み、API取得による確認        |

自動E2Eテスト、性能テスト、脆弱性スキャンはMVP対象外とする。

## 3. テストケース管理

- テスト観点と結果は本ドキュメントで管理する
- 不具合や追加対応が必要な内容はGitHub Issuesまたはチーム内で共有する
- テストケースIDは、必要に応じて`AUTH-001`、`REPORT-001`など、対象機能ごとに採番する

## 4. テスト環境

- フロントエンド：Next.js
- バックエンド：FastAPI
- データベース：PostgreSQL
- 起動環境：Docker Compose
- フロントエンド：`http://localhost:3000`
- バックエンド：`http://localhost:8000`
- Swagger UI：`http://localhost:8000/docs`
- `student`および`teacher`の確認にはseedデータを利用する

## 5. 受け入れ基準（Definition of Done）

- Docker Composeでfrontend、backend、dbが起動する
- ログイン・ログアウトが正常に動作する
- `student`が自分の投稿を作成・一覧表示・詳細表示・編集・削除できる
- `teacher`が生徒全員分の投稿を一覧・詳細表示できる
- 未認証時や権限外操作時に適切なエラーまたは画面遷移となる
- 投稿データがPostgreSQLへ保存され、再取得できる
- デモに必要な主要操作をブラウザ上で実行できる

## 6. reports API のテスト設計

### 6.1 正常系のテスト観点

- 認証済みの `student` で `reports API` を呼び出すと、正常に一覧または詳細が取得できること
- 認証済みの `teacher` で `reports API` を呼び出すと、正常に一覧または詳細が取得できること
- 返却項目に必要な情報が含まれていること
- `DB seed` の前提データに対して、期待した件数と内容が返ること

### 6.2 異常系のテスト観点

- 未認証で `reports API` を呼び出すと `401 Unauthorized` になること
- 権限のないユーザーが呼び出すと `403 Forbidden` になること
- 不正な入力値を渡した場合に、`400 Bad Request`または`422 Unprocessable Entity`など、実装に応じたエラーが返ること
- 存在しないデータを指定した場合に適切なエラーが返ること
- DB 接続エラー時に適切なエラー処理が行われること

### 6.3 student / teacher の権限別テスト観点

- `student` は自分に許可された範囲のデータのみ参照できること
- `teacher` は `teacher` 権限として許可された範囲のデータを参照できること
- ロールによって返却されるデータ内容が変わること
- 権限外の操作ができないこと

### 6.4 DB 接続・seed データ前提の確認観点

- テスト実行時に DB 接続が確立していること
- `seed` データが正しく投入されていること
- テスト前提となるデータが毎回再現可能であること
- 依存する関連データが欠けていないこと

### 6.5 統合テストシナリオ

- ログインする
- `reports API` を呼び出す
- 取得結果を確認する
- `student` と `teacher` の両ロールで結果差分を確認する
- 未認証時のエラー応答を確認する
- 不正値入力時のエラー応答を確認する

### 6.6 自動化候補と手動確認項目

#### 継続開発時に自動化を検討するテスト

- 認証APIの正常系・異常系
- 投稿CRUD APIの正常系
- `401`、`403`、`404`、`422`などの代表的な異常系
- student／teacherの基本的な権限確認
- studentが他人の投稿を操作できないこと

#### MVPで手動確認するテスト

- 画面表示とレイアウト
- ログイン後のrole別画面遷移
- 投稿作成・一覧・詳細・編集・削除の操作フロー
- 投稿種別の切り替え
- ログアウト
- 不正JWT・未認証時の画面遷移
- Docker Compose環境でのfrontend・backend・db連携
- デモ前の最終確認

### 6.8 確認で判明した課題

#### DB接続エラー時の例外処理

DBを停止した状態で、認証済みユーザーによる`GET /reports`を実行したところ、以下を確認した。

- APIは`500 Internal Server Error`を返した
- バックエンドでは`sqlalchemy.exc.OperationalError`が発生した
- スタックトレースがバックエンドログへ出力された
- バックエンドプロセス自体は停止せず、継続して稼働した
- DB再起動後、`GET /health/db`が`200 OK`となり、接続が復旧した

現状、DB接続エラー専用の例外処理や、利用者向けの共通エラーレスポンスは実装していない。

継続開発時には、DB接続エラーを捕捉し、内部情報を利用者へ返さず、`500 Internal Server Error`または`503 Service Unavailable`として統一されたエラーレスポンスを返す処理を検討する。
