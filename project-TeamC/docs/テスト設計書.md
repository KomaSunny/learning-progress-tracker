# テスト設計書

## 1. テスト方針

- 目的・品質ゴール
- カバレッジ目標（例：ライン 80% 以上）
- テストピラミッドの考え方（単体 > 結合 > E2E）

## 2. テスト種別と範囲

| 種別         | 対象                     | ツール               | 担当 |
| ------------ | ------------------------ | -------------------- | ---- |
| 単体テスト   | 関数・コンポーネント単位 | Jest / Vitest        |      |
| 結合テスト   | API ・モジュール間       | Supertest 等         |      |
| E2E テスト   | ユーザー操作のシナリオ   | Playwright / Cypress |      |
| 性能テスト   | 想定負荷でのレイテンシ   | k6 / JMeter          |      |
| セキュリティ | 認証・認可・OWASP Top 10 | OWASP ZAP 等         |      |

## 3. テストケース管理

- 管理場所（リポジトリ / スプレッドシート / TestRail 等）
- ID 採番ルール
- 不具合のチケット化フロー

## 4. テスト環境

- 開発 / ステージング / 本番の差分
- テストデータ作成方針

## 5. 受け入れ基準（Definition of Done）

- 全テストが green
- カバレッジ基準を満たす
- セキュリティスキャンで重大な指摘がない

## 6. reports API のテスト設計

### 6.1 正常系のテスト観点

- 認証済みの `student` で `reports API` を呼び出すと、正常に一覧または詳細が取得できること
- 認証済みの `teacher` で `reports API` を呼び出すと、正常に一覧または詳細が取得できること
- 返却項目に必要な情報が含まれていること
- `DB seed` の前提データに対して、期待した件数と内容が返ること

### 6.2 異常系のテスト観点

- 未認証で `reports API` を呼び出すと `401 Unauthorized` になること
- 権限のないユーザーが呼び出すと `403 Forbidden` になること
- 不正なパラメータを渡した場合に `400 Bad Request` になること
- 存在しないデータを指定した場合に適切なエラーが返ること
- DB 接続エラー時に適切なエラー処理が行われること

### 6.3 student / teacher の権限別テスト観点

- `student` は自分に許可された範囲のデータのみ参照できること
- `teacher` は `teacher` 権限として許可された範囲のデータを参照できること
- ロールによって返却されるデータ内容が変わること
- 権限外の操作ができないこと

### 6.4 DB 接続・seed データ前提の確認観点

- テスト実行時に DB 接続が確立していること
- `seed` データが正しく投入されていること
- テスト前提となるデータが毎回再現可能であること
- 依存する関連データが欠けていないこと

### 6.5 統合テストシナリオ

- ログインする
- `reports API` を呼び出す
- 取得結果を確認する
- `student` と `teacher` の両ロールで結果差分を確認する
- 未認証時のエラー応答を確認する
- 不正値入力時のエラー応答を確認する

### 6.6 自動化するテストと手動確認するテスト

- 自動化するテスト
  - 正常系の主要ケース
  - `401` / `403` などの代表的な異常系
  - ロールごとの基本的な権限確認
- 手動確認するテスト
  - 画面表示や一覧の見え方
  - 実際の操作フロー
  - デモ前の最終確認
