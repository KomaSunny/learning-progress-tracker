# 技術選定

## 1. 選定方針

本プロジェクトでは、1週間のチーム開発でMVPを完成させることを優先し、以下の観点から技術を選定した。

- チームで学習しながら実装しやすいこと
- フロントエンド、バックエンド、データベースの役割を分けやすいこと
- API開発、認証・認可、DB操作の流れを学習しやすいこと
- MVPに必要な機能を短期間で実装しやすいこと
- 将来的に機能追加しやすい構成であること

## 3. 比較サマリ

### フロントエンド

フロントエンドは Next.js / TypeScript を採用する。

Next.js は画面遷移やページ単位の開発がしやすく、TypeScript と組み合わせることで、データの型を意識しながら実装できる。  
今回のアプリでは、ログイン画面、ダッシュボード、投稿作成画面、投稿編集画面など複数の画面が必要になるため、Next.js が適していると判断した。

### バックエンド

バックエンドは Python / FastAPI を採用する。

候補として FastAPI、Django、Flask があるが、今回のバックエンドは画面を返すのではなく、認証・認可・DB操作を行うAPIサーバーとして実装する。  
FastAPI はAPI開発に向いており、Pydanticによる入力値検証や自動APIドキュメント生成ができるため、フロントエンド担当者ともAPI仕様を共有しやすい。

今回のMVPでは、JWT認証、ログイン中ユーザーの取得、role別の認可制御、投稿CRUD APIを実装する。

### データベース

データベースは PostgreSQL を採用する。

ユーザー情報、投稿、権限情報など、関連するデータを扱うため、リレーショナルデータベースが適している。  
PostgreSQL は実務でも利用例が多く、チーム開発の学習にも向いている。

今回のMVPでは、`users` テーブルと `reports` テーブルを中心に構成する。
投稿には `type` を持たせ、将来的に `daily_report` / `progress_report` を区別できるようにする。

### ORM

ORMは SQLModel を採用する。

SQLModel はFastAPIとの相性がよく、Pydanticに近い書き方がでモデル定義ができるため、学習しながら実装しやすい。
また、SQLAlchemyをベースとしているため、必要に応じてSQLAlchemyの機能も参照できる。

SQLAlchemy はPythonで広く利用されているORMで、情報量が多く、PostgreSQLとの相性も良い。

### 認証・認可

認証方式は JWTを採用する。

JWTを利用することで、ログイン後に発行されたトークンをフロントエンドが保持し、APIリクエスト時に `Authorization` ヘッダーへ付与して送信できる。  
バックエンド側でJWTを検証し、ログイン中のユーザーを特定する。

Firebase Authなどの外部認証サービスは使用せず、認証・認可の基本的な仕組みを学習する目的でJWTを採用する。

今回のMVPでは、`student` / `teacher` のroleによって利用できる機能を分離する。
`student` は自分の投稿のみ作成・一覧表示・編集・削除でき、`teacher` は生徒全員分の投稿を一覧表示できる。

### コンテナ

Docker / Docker Compose を利用する。

frontend、backend、dbをそれぞれコンテナとして起動できる構成にすることで、メンバー間の開発環境差を減らしやすくする。  
MVPでは最低限、以下の3つのコンテナを想定する。

- frontend：Next.js
- backend：FastAPI
- db：PostgreSQL

## 4. 現在の制約

- 本番環境へのデプロイはMVP対象外
- CI / CDは未導入
- 新規登録機能は未実装
- teacherによる投稿の作成・編集・削除は対象外
- 絞り込み、確認ステータス、ページネーションは未実装
- PCブラウザでの利用を優先している

## 5. リスクと対応

| リスク                                                            | 対応方針                                                                                                                                                        |
| ----------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| FastAPIやPythonバックエンドの学習コストがある                     | MVPでは基本的なAPI実装に絞り、ログインと投稿CRUDを優先する                                                                                                      |
| JWT認証・認可の実装が複雑になる                                   | MVPでは、`student` は自分の投稿のみ作成・一覧表示・編集・削除でき、`teacher` は生徒全員分の投稿を一覧表示できる範囲に絞る                                       |
| ORM選定で迷う可能性がある                                         | SQLModelを第一候補とし、必要に応じてSQLAlchemyの機能も参照する                                                                                                  |
| Docker環境構築に時間がかかる可能性がある                          | 最初はローカル起動でも進められるようにし、必要に応じてDocker Composeを整える                                                                                    |
| 投稿種別の切り替えUIまで実装する時間が足りない可能性がある        | DB/APIには `type` を持たせるが、画面での選択UIが間に合わない場合は `progress_report` をデフォルト値として扱う                                                   |
| teacher向けの詳細な管理機能まで実装する時間が足りない可能性がある | MVPでは /dashboard のrole別表示に絞り、teacher は生徒全員分の投稿一覧を閲覧できるところまで実装する。絞り込み、ステータス管理、専用管理画面はGood to haveとする |
| フロントエンドとバックエンドの接続で認識ズレが起きる可能性がある  | API設計を先に整理し、エンドポイントとリクエスト/レスポンスを明確にする                                                                                          |
