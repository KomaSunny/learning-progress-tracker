# セキュリティ設計

## 1. 脅威モデル

### 想定する脅威アクター

- 未ログインユーザー
- 他人の投稿を閲覧・編集しようとするログイン済みユーザー
- 不正なJWTを使ってAPIへアクセスしようとするユーザー
- 自分に許可されていない操作を実行しようとするユーザー
- パスワードを推測してログインを試みるユーザー

### 守るべき資産

- ユーザー情報
  - 名前
  - メールアドレス
  - パスワードハッシュ
  - 権限情報
- 投稿データ
  - 投稿種別
  - タイトル
  - 学習内容
  - 困りごと
  - 次にやること
  - 学習時間
  - 理解度
- 認証情報
  - JWT
  - パスワード

### 想定攻撃シナリオ

| 脅威                      | 内容                                                           | 対策方針                                                             |
| ------------------------- | -------------------------------------------------------------- | -------------------------------------------------------------------- |
| なりすまし                | 他人のメールアドレス・パスワードでログインされる               | パスワードをハッシュ化し、ログインAPIで認証する                      |
| 不正なJWT利用             | 改ざんされたJWTや期限切れJWTでAPIへアクセスされる              | JWTの署名と有効期限をバックエンド側で検証する                        |
| 権限昇格                  | `student`が`teacher`として利用できる機能へアクセスしようとする | バックエンド側でroleを確認し、許可された操作のみ実行できるようにする |
| 他人の投稿操作            | `student`が自分以外の投稿を取得・編集・削除しようとする        | バックエンド側で投稿者IDとログイン中ユーザーIDを照合する             |
| `teacher`による対象外操作 | `teacher` が投稿の作成・更新・削除を実行しようとする           | MVPでは閲覧のみ許可し、作成・更新・削除は拒否する                    |
| 情報漏えい                | JWTやパスワードがログに出力される                              | 機密情報をログに出さない                                             |
| 入力値攻撃                | 不正な入力値でAPIにアクセスされる                              | バックエンド側でバリデーションを行う                                 |

## 2. 認証・認可

### 認証方式

- MVPではJWT認証を採用する
- ログイン成功時にJWTを発行する
- フロントエンドは、認証が必要なAPIへアクセスするときにJWTを送信する
- バックエンドはJWTを検証し、ログイン中ユーザーを特定する

### 認証ヘッダー

```http
Authorization: Bearer <JWT>
```

### パスワード管理

- パスワードは平文で保存しない
- バックエンド側でハッシュ化して保存する
- ハッシュアルゴリズムは、bcrypt または argon2 を検討する

### トークン管理

- JWTにはログイン中ユーザーを識別できる情報を含める
- JWTにはユーザーIDやroleを含める想定
- JWTには有効期限を設定する
- MVPではリフレッシュトークンは必須としない
- 必要になった場合は、リフレッシュトークン方式を検討する

###JWTの保存方針

- MVPでは、フロントエンド側でJWTを保持する
- localStorage または sessionStorage を利用する場合は、XSS対策を徹底する
- 本番運用では、HttpOnly Cookieなど、より安全な保存方法も検討する
- JWTをログや画面上に出力しない

### 認可

- 権限判定はフロントエンドではなく、バックエンド側で必ず行う
- フロントエンドでボタンを非表示にしていても、API側でも必ず認可チェックを行う
- フロントエンドから送られた `user_id` は信用しない
- 投稿作成時の投稿者IDは、JWTから取得したログイン中ユーザーIDを使用する
- G`ET /reports` は、ログイン中ユーザーのroleによって返却範囲を切り替える
  - `student`：自分の投稿のみ取得できる
  - `teacher`：生徒全員分の投稿を取得できる
- `student` は、自分の投稿のみ作成・取得・更新・削除できる
- `teacher` は、生徒全員分の投稿を一覧・詳細表示できる
- MVPでは、`teacher` による投稿の作成・更新・削除は対象外とする
- `teacher` が投稿の作成・更新・削除APIを実行した場合は、`403 Forbidden` を返す
- `student` が他人の投稿を取得・更新・削除しようとした場合は、`403 Forbidden` または `404 Not Found` を返す

## 3. 通信のセキュリティ

- 本番環境ではHTTPSを利用する
- 開発環境では `http://localhost` を利用する
- CORSは、許可するフロントエンドのURLを限定する
- 本番環境では、不要なオリジンからのアクセスを許可しない
- Cookieを利用する場合は、`HttpOnly`、`Secure`、`SameSite` の設定を検討する

---

## 4. 入力・出力対策（OWASP Top 10）

### SQLインジェクション対策

- SQLを直接文字列で組み立てない
- ORMを利用し、パラメータ化されたクエリを使う
- 入力値はバックエンド側でバリデーションする

### XSS対策

- ユーザー入力を画面に表示する場合は、HTMLとしてそのまま埋め込まない
- React / Next.js の標準的なエスケープ処理を利用する
- `dangerouslySetInnerHTML` は原則使用しない
- JWTをlocalStorageまたはsessionStorageに保存する場合は、XSSによりトークンが盗まれるリスクがあるため、不要なHTML挿入を避ける

### CSRF対策

- MVPではJWTを `Authorization` ヘッダーで送信する想定のため、CookieベースのCSRFリスクは低め
- Cookieで認証情報を管理する場合は、`SameSite` やCSRFトークンを検討する

### 入力バリデーション

- メールアドレスは形式チェックを行う
- パスワードは必須入力とする
- 投稿種別は `daily_report` または `progress_report` とする
- 投稿種別が未指定の場合は `progress_report` をデフォルト値として扱う
- 投稿タイトルは必須、255文字以内とする
- 投稿本文は必須とする
- 学習時間は0以上の数値とする
- 理解度は1〜5の範囲とする

### 出力制御

- APIレスポンスには、必要以上のユーザー情報を含めない
- `teacher` 向けの投稿一覧では、誰の投稿か分かるように投稿者名を返却する
- パスワードハッシュはAPIレスポンスに含めない
- JWTやDB接続情報などの機密情報はAPIレスポンスに含めない

### レート制限 / Bot対策

- MVPでは厳密なレート制限は実装しない
- ログインAPIについては、連続試行による不正ログイン対策が必要になる可能性がある
- 将来的に、ログイン試行回数の制限を検討する

## 5. 機密情報の取り扱い

### シークレット管理

- JWTの署名に使う秘密鍵は、コードに直接書かない
- DB接続情報は、コードに直接書かず環境変数で管理する
- `.env` ファイルはGitHubにpushしない
- `.env.example` を用意し、必要な環境変数名のみ共有する
- 本番環境では、環境変数またはシークレット管理サービスで管理する

### ログ・エラーメッセージ

- パスワード、JWT、DB接続情報をログに出力しない
- エラーメッセージに内部情報を出しすぎない
- APIエラーは、共通のエラーレスポンス形式で返す
- 認証失敗時は、メールアドレスが存在するかどうかを推測しにくいメッセージにする

### 個人情報の扱い

- ユーザーのメールアドレスは必要な画面・APIでのみ扱う
- `teacher`向け画面では、必要な範囲のユーザー情報のみ表示する
- 投稿一覧で表示する投稿者情報は、原則として投稿者名に限定する
- 不要な個人情報はDBに保存しない

---

## 6. インフラ・運用面のセキュリティ

- 本番環境ではHTTPSを利用する
- DBは外部から直接アクセスできない構成を検討する
- 依存パッケージは定期的に更新する
- GitHubのDependabotなどを利用し、脆弱性通知を確認する
- Dockerを利用する場合は、不要なポートを公開しない
- 本番環境の環境変数は、チーム内でも必要な人だけが扱う
- `.env`、秘密鍵、DB接続情報、JWT秘密鍵などをGitHubにpushしない

---

## 7. 監査・インシデント対応

### 監査ログ

MVPでは詳細な監査ログは実装しない。  
ただし、将来的には以下の操作ログを残すことを検討する。

- ログイン成功・失敗
- 投稿の作成
- 投稿の更新
- 投稿の削除
- 講師による投稿閲覧
- 権限のない操作が行われた履歴

### インシデント対応

- 不正アクセスが疑われる場合は、チーム内で速やかに共有する
- 必要に応じて、該当ユーザーのアカウント停止やパスワード変更を行う
- JWT秘密鍵が漏えいした場合は、秘密鍵を更新し、既存トークンを無効化する
- `.env` や秘密鍵を誤ってGitHubにpushした場合は、該当情報を無効化・再発行する
