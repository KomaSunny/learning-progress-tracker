# セキュリティ設計

## 1. 脅威モデル

### 想定する脅威アクター

- 未ログインユーザー
- 他人の投稿を閲覧・編集しようとするログイン済みユーザー
- 不正なJWTを使ってAPIへアクセスしようとするユーザー
- パスワードを推測してログインを試みるユーザー

### 守るべき資産

- ユーザー情報
  - 名前
  - メールアドレス
  - パスワードハッシュ
  - 権限情報
- 日報・学習進捗データ
  - 学習内容
  - 困りごと
  - 次にやること
  - 学習時間
  - 理解度
- 認証情報
  - JWT
  - パスワード

### 想定攻撃シナリオ

| 脅威           | 内容                                             | 対策方針                                        |
| -------------- | ------------------------------------------------ | ----------------------------------------------- |
| なりすまし     | 他人のメールアドレス・パスワードでログインされる | パスワードをハッシュ化し、ログインAPIで認証する |
| 権限昇格       | 学生ユーザーが講師用APIを利用しようとする        | `role` を確認し、講師のみアクセス可能にする     |
| 他人の投稿操作 | 自分以外の投稿を取得・編集・削除しようとする     | バックエンド側で投稿者IDを確認する              |
| 情報漏えい     | JWTやパスワードがログに出力される                | 機密情報をログに出さない                        |
| 入力値攻撃     | 不正な入力値でAPIにアクセスされる                | バリデーションを行う                            |

## 2. 認証・認可

### 認証方式

- MVPではJWT認証を採用する
- ログイン成功時にJWTを発行する
- フロントエンドは、認証が必要なAPIへアクセスするときにJWTを送信する

### 認証ヘッダー

```http
Authorization: Bearer <JWT>
```

### パスワード管理

- パスワードは平文で保存しない
- バックエンド側でハッシュ化して保存する
- ハッシュアルゴリズムは、bcrypt または argon2 を検討する

### トークン管理

- JWTにはユーザーIDや権限情報を含める
- JWTには有効期限を設定する
- MVPではリフレッシュトークンは必須としない
- 必要になった場合は、リフレッシュトークン方式を検討する

### 認可

- 学生ユーザーは、自分の投稿のみ取得・編集・削除できる
- 講師ユーザーは、Good to haveとして全員分の投稿を閲覧できる
- 権限判定はフロントエンドではなく、バックエンド側で必ず行う
- フロントエンドから送られた `user_id` は信用しない
- JWTからログイン中のユーザーを特定する

---

## 3. 通信のセキュリティ

- 本番環境ではHTTPSを利用する
- 開発環境では `http://localhost` を利用する
- CORSは、許可するフロントエンドのURLを限定する
- 本番環境では、不要なオリジンからのアクセスを許可しない
- Cookieを利用する場合は、`HttpOnly`、`Secure`、`SameSite` の設定を検討する

---

## 4. 入力・出力対策（OWASP Top 10）

### SQLインジェクション対策

- SQLを直接文字列で組み立てない
- ORMを利用し、パラメータ化されたクエリを使う
- 入力値はバックエンド側でバリデーションする

### XSS対策

- ユーザー入力を画面に表示する場合は、HTMLとしてそのまま埋め込まない
- React / Next.js の標準的なエスケープ処理を利用する
- `dangerouslySetInnerHTML` は原則使用しない

### CSRF対策

- MVPではJWTを `Authorization` ヘッダーで送信する想定のため、CookieベースのCSRFリスクは低め
- Cookieで認証情報を管理する場合は、`SameSite` やCSRFトークンを検討する

### 入力バリデーション

- メールアドレスは形式チェックを行う
- パスワードは必須入力とする
- 投稿タイトルは必須、255文字以内とする
- 投稿本文は必須とする
- 学習時間は0以上の数値とする
- 理解度は1〜5の範囲とする

### レート制限 / Bot対策

- MVPでは厳密なレート制限は実装しない
- ログインAPIについては、連続試行による不正ログイン対策が必要になる可能性がある
- 将来的に、ログイン試行回数の制限を検討する

---

## 5. 機密情報の取り扱い

### シークレット管理

- JWTの署名に使う秘密鍵は、コードに直接書かない
- DB接続情報は、コードに直接書かず環境変数で管理する
- `.env` ファイルはGitHubにpushしない
- 本番環境では、環境変数またはシークレット管理サービスで管理する

### ログ・エラーメッセージ

- パスワード、JWT、DB接続情報をログに出力しない
- エラーメッセージに内部情報を出しすぎない
- APIエラーは、共通のエラーレスポンス形式で返す

### 個人情報の扱い

- ユーザーのメールアドレスは必要な画面・APIでのみ扱う
- 講師用画面では、必要な範囲のユーザー情報のみ表示する
- 不要な個人情報はDBに保存しない

---

## 6. インフラ・運用面のセキュリティ

- 本番環境ではHTTPSを利用する
- DBは外部から直接アクセスできない構成を検討する
- 依存パッケージは定期的に更新する
- GitHubのDependabotなどを利用し、脆弱性通知を確認する
- Dockerを利用する場合は、不要なポートを公開しない
- 本番環境の環境変数は、チーム内でも必要な人だけが扱う

---

## 7. 監査・インシデント対応

### 監査ログ

MVPでは詳細な監査ログは実装しない。  
ただし、将来的には以下の操作ログを残すことを検討する。

- ログイン成功・失敗
- 投稿の作成
- 投稿の更新
- 投稿の削除
- 講師による投稿閲覧

### インシデント対応

- 不正アクセスが疑われる場合は、チーム内で速やかに共有する
- 必要に応じて、該当ユーザーのアカウント停止やパスワード変更を行う
- JWT秘密鍵が漏えいした場合は、秘密鍵を更新し、既存トークンを無効化する
